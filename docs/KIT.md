# 工作台设计套件与自动质检（W1）

用户的要求：工作台按一句话生成，**生成出来的必须是商业级品质，不能像毕业设计**；不预设品类，生成器自己拓展。
做法是两件东西兜底：

1. **零件库**（`web/kit/`）：所有生成的窗口都从这里拼，外观、动效、明暗、手机适配一次做好，品质有底线。
2. **自动质检**（`core/benchkit/quality.py`，命令 `roundtable kit-check`）：生成的页面必须过关，不过关就带着问题清单打回重做。

生成逻辑本身（拆需求 → 找插件 / 拼零件 / 缺件现做 → 质检打回 → 迭代）是下一段 W2，见本文末尾。

## 零件库 `web/kit/`

| 文件 | 内容 |
|---|---|
| `kit.css` | 令牌（`--k-*` 颜色、圆角、阴影、动效时长）、6 个主题预设（深浅各一套）、外壳与 12 列网格、卡片、指标卡、按钮与表单、标签与进度、列表与表格、图片卡、空状态与骨架、会话窗、页签 / 弹窗 / 提示、图表、时间线、看板、月历、地图框、查看器、编辑器框、清单 |
| `kit.js` | 原生 ES 模块，不依赖任何库：折线 / 柱状 / 环形 / 迷你趋势 / 进度环 / 日历热力图、可排序表格、时间线、看板（拖动 + 键盘）、月历、示意地图（按经纬度，不联网）、图片视频查看器、编辑器框、清单、会话窗（正在输入、快捷问题、`onAsk` 接真会话）、分段按钮、提示条、空状态、本机存储、数字格式 |
| `icons.js` | 图标（Lucide 子集，ISC 许可，见 `CREDITS.md`） |
| `manifest.json` | **零件清单**：每个零件的用途和调用方式。生成器按清单挑零件；新零件过了质检再加进来（测试检查清单和代码对得上） |
| `gallery.html` | 样板页：所有零件的真实用法，也是质检的基准页（测试要求满分） |

用法：

```html
<html lang="zh-CN" data-k-theme="paper">
<link rel="stylesheet" href="/kit/kit.css">
<body class="k-root"><div class="k-page"> … </div>
<script type="module">
  import { lineChart, chat } from '/kit/kit.js';
</script>
```

规则：颜色只用 `--k-*` 变量；每个窗口都要有没数据时的样子；按钮、图片、图表都要有名字或说明；手机宽度不横向滚动。
主题跟系统明暗，`data-k-mode="light|dark"` 可强制；`prefers-reduced-motion` 时动效全部关掉。
套件不引任何外部资源（字体用系统字体，测试守着）。

在圆桌里打开 `http://127.0.0.1:8000/kit/gallery.html` 可以看样板页，右上角切主题和明暗。

## 自动质检

```bash
roundtable kit-check 页面.html -o 质检结果/      # 也可以是 http(s) 地址
```

用 Playwright 在 **电脑 1280 / 平板 820 / 手机 390 × 浅色 / 深色** 共 6 种组合下打开页面（本地文件自带一个只在本机的静态服务，`/kit/` 指向零件库；本机以外的请求一律中止，不联网），每种组合截一张全页图，量这些：

| 检查 | 级别 | 说明 |
|---|---|---|
| 页面报错 | 必须修 | 脚本异常、控制台错误 |
| 没有声明编码 | 必须修 | 没写 `<meta charset="utf-8">`，中文会乱码 |
| 横向溢出 | 必须修 | 页面比屏幕宽（表格、看板、页签自带横向滚动的除外） |
| 坏字 | 必须修 | 页面上出现 undefined、NaN、[object Object] 等 |
| 没用设计套件 | 必须修 | 没引 `kit.css` 或没有 `k-root` |
| 外链脚本 | 必须修 | 本机和 cdnjs / jsdelivr / unpkg 以外的脚本 |
| 按钮没有名字、图片没有说明、图片打不开、图表空白 | 必须修 | 图表没数据也要显示空状态 |
| 对比度不够 | 低于 3:1 必须修，3～4.5 建议修 | 按 WCAG，大字 3:1；压在图片或图形上的字不量 |
| 字太小 | 建议修 | 小于 12px |
| 手机上按钮太小 | 建议修 | 小于 32px |

结果：100 分起扣（必须修每条 15 分，建议修每条 3 分），**有必须修的就是不通过**。`-o` 目录里有 6 张截图和 `report.json`。
命令返回码：通过 0、不通过 1、没法检查 2（没装 Playwright 时提示安装；浏览器版本不匹配时用 `ROUNDTABLE_CHROMIUM` 指定）。

硬指标只保证「不出错、不难看」。「像不像商业产品」由 W2 的截图评分负责（截图交给模型按标准逐项打分，不过线带着理由打回）。

## W2 生成逻辑（2026-10-29 已做）

一句话进来，走这几步，全程在 `data/bench/<编号>/` 这个工作文件夹里（不进仓库）：

1. **拆需求**（`bench_plan`）：任意一句话 → 规格 `spec.json`：标题、主题、窗口（用途、零件、数据、操作）、还缺什么（`needs`，带英文搜索词）。程序校验并修正：编号规范、只留认得的零件和图标、宽度 3～12、窗口不超过 `max_windows`。
2. **外壳由程序画**：顶栏、网格、每个窗口的卡片按规格生成，品质稳定。每个窗口单独加载，坏了只影响自己那一格。
3. **找插件**（`scout.py`）：按 `needs` 搜 dsh 插件集市索引和 GitHub。
   - GitHub ≥ `min_stars` 星、许可证宽松（MIT、Apache-2.0、BSD、ISC 等）、没归档、不太大、说明里不提 key / 登录 / 上传：**直接搬**。钉在某个提交上，只下载源码包、只解压不运行（挡掉绝对路径、`..`、链接、超大文件），放进 `vendor/`，来源、许可证、星数、提交号、sha256 记进 `sources.json`。
   - 其余只借思路：交给写窗口的助手参考做法、自己写。
4. **分头写窗口**（`bench_window`）：超级电脑按擅长、余额、忙闲挑助手，各写 `windows/<id>.js`（导出 `mount(el, ctx)`）和 `data/<id>.json`。零件库不够用时先看 `parts/`，还没有就自己做通用零件 `parts/名字.js`（开头一行 `// part: 名字 — 用途`）。
5. **质检 + 评审**：先过 `kit-check`，再把截图交给评审（`bench_review`）按 `rubric` 七项打分。**按作者分组，评审永远不是作者本人**；只有一位助手时没人能评，直接停下来等你。
6. **打回返工**（`bench_rework`）：没过线（平均 ≥ `pass_avg`、每项 ≥ `pass_min`、质检通过）就带着扣分理由交回原作者重做；最多 `max_rounds` 轮，还不过就停下来等你看。
7. **自行拓展**（`library.py`）：过线以后，`parts/` 里新做的零件收进本机零件库 `data/bench/_library/parts/`，以后每个工作台都先拷进来、拆需求时也能看到；整个台存成配方 `_library/recipes/`。仓库里的 `web/kit/` 不会被自动改。

**安全**：生成的页面在 `/bench/<编号>/` 下用 CSP 沙箱打开（独立来源，碰不到 `/api` 和登录状态），聊天零件经 postMessage 提问。

接口：`GET/POST /api/bench`（状态 / 提交一句话）、`POST /api/bench/cancel`、`GET /api/bench/<编号>`；成品在 `/bench/<编号>/index.html`。

## W3 控制室（2026-10-29 已做）

圆桌顶部「工作台」→「生成器」标签（默认标签）：
- 一句话输入，点「生成工作台」。
- 进度条：拆需求 → 找插件 → 分头写 → 质检评审 → 返工 → 过线（没走的一格标「跳过」）。
- 窗口分工表（谁写的、返工几次）、插件清单（为了什么、仓库、许可证、星数、直接用还是只借思路、为什么）、这次新收进零件库的零件。
- 每轮：质检分数和问题、评审七项分数条、截图（点开看大图）、谁评了谁的窗口和意见。
- 过线或「等你决定」后可以「打开成品」：在下方沙箱 iframe 里运行；成品里的对话窗经 postMessage 交给 `POST /api/bench/<编号>/ask`，由一位助手（`bench.ask_kind`，花订阅次数）按这个台的规格和数据回答（提示词 `bench_ask`，在 `ask/` 子文件夹里跑，不改台本身）。只认圆桌自己嵌进来的那个 iframe。
- 「在新窗口打开」也行，但那样对话窗不能用。

## W4 第一次真跑后的修正（2026-10-30）

用户的第一句（旅行台：吃穿住行玩全覆盖、可按婚礼生日等定制、商用级、手机好用）在用户电脑上用真实助手跑了 52 分钟，3 轮都没过线（平均 5.76）。按「改逻辑不改样品」修了这些：
- **质检误判**：只有图标的按钮，文字里有空白时被当成「有文字」，再去掉空白就成了空名字，判成「按钮没有名字」，三轮都卡在这里，评审又因此压分。现在每个候选名字先去空白再挑，图标的 aria-label / title、图片 alt 都算名字。
- **问题按窗口交回**：质检测到的每个问题都记下出在哪个窗口（`Finding.windows`），返工时只交给那几个窗口的作者；评审「质检没过就压分」也只限出问题的窗口。
- **手机长度**：手机上一个窗口超过 2 屏是「建议修」，超过 4 屏是「必须修」（`窗口太长`）。
- **读代码检查**（`lint.py`）：窗口没用零件库（`ctx.kit` 或 `/kit/kit.js`）是「必须修」；写死颜色超过 3 处、代码超过 60KB 是「建议修」。
- **共用信息和消息约定**：拆需求时多给两样（`bench_plan` v2）：`shared` 放各窗口共用的基本信息（日期、人数和年龄、币种、场景……），写成 `data/_shared.json`，窗口从 `ctx.shared` 读；`events` 规定窗口之间的消息名字、谁发谁收、detail 字段。写窗口、返工、评审的提示词（v2）都按这个要求和检查。
- **不画简笔画、不做假按钮**：没有真图用图标和真实信息；实时信息标「数据截至」，不做假的「刷新」。
- **找插件更准**：dsh 集市关键词至少命中两个；只借思路的候选不到 20 星不列进清单。
- **写完先自测**（第二次真跑时发现一个窗口的选择器写错，整个设置窗口崩了，到评审才发现）：窗口全部写完后先在电脑·浅色下开一次页面，脚本报错（外壳记成「窗口 xxx 出错」，据此认出是哪个窗口）、没用零件库，当场交回作者改，不占评审轮次。
- **先看草稿**：控制室里只要有窗口写好了，就出现「先看草稿」，跑到一半也能打开看。

## W4 第二次真跑后的修正（2026-10-30）

第二次跑了 67 分钟，第 3 轮质检通过（97 分），评审 6.0 分（第一次 5.76）。146 条评审意见里最多的是：窗口之间「已加入」对不上（各窗口各存一份）、手机首屏被筛选和说明挤满、圆环里的字只有 8px、「吃」每 2 秒轮询一次存储；而且评审每轮换一批新问题，分数不升反降。修了这些：
- **共用的用户数据 `ctx.state`**：拆需求时多给一样 `state`（几个窗口一起读写的数据：键 → 结构，`bench_plan` v3）。外壳给每个窗口一个 `ctx.state`（零件 `sharedState`：`get` / `set` / `update` / `on`），谁改了大家都收到；「已加入」「已付」这类标记都从它算，不各存一份。
- **评审用同一把尺子**（`bench_review` v3）：第 2 轮起评审先拿到上一轮对这几个窗口提的问题，逐条核对改了没有；改好的不再扣分，新发现的小瑕疵只记下不压分，只有坏了、数据错、手机上用不了才能让分数降。
- **读代码检查**：解构写法（`const { kit } = ctx`、`const { seg } = kit`）也算用了零件库（第二次真跑的误报）；`setInterval` 记成「轮询定时器」（建议修）。
- **零件修正**：小圆环的数字不小于 14px，说明字放到圆环下面，不叠在一起。
- **手机首屏**（写窗口、返工 v3）：先给结论、下一步、关键数字，筛选和说明收进折叠；一张卡片最多一个主按钮。

## 拿用户的要求和底线来验收（2026-10-30）

用户看了第二次的成品，说「完全不符合我的要求」，并指出之前给的参考资料（DSH 工作台的 7 个成品）是他的**底线**。对照之后（`/mnt/project-files/验收/W4_旅行台_第2次_差距.md`）发现两个根本问题：评审只打通用分，没拿用户的要求去验收；成品是一份编好的样品，不能拿来处理用户自己的情况。改了这些（只用假助手测试，没有真跑）：
- **验收清单**（`spec.requirements`）：拆需求时把用户的原话拆成几条能检查的要求（r1…，最多 `bench.max_requirements` 条），再加上配置里的底线（`bench.baseline`，b1…，原文以配置为准），每条写怎么检查、归哪几个窗口。评审（`bench_review` v4）逐条判做到没有；至少一位评审判过、且判过的都说做到才算做到（`merge_checks`）。**有一条没做到就不过线**，没做到的要求排在返工意见最前面，只交给负责的窗口。控制室每轮显示「验收 x/y」和逐条结果。
- **底线**（`config/roundtable.yaml` 的 `bench.baseline`，可改）：主视觉占大半屏；不让助手自己画插图；点一下能联动；有自己的主色和标题风格；数据有真实来源；能按用户自己的情况用；手机顺手。
- **主视觉**（`spec.hero`）：主视觉窗口排最前、至少 8 列，外壳给它加 `k-hero`（内容区贴边、更高）。零件库新增 `k-display`（大号标语）、`k-kicker`（小号字距标签）、`k-media`（带来源的真照片）。
- **自己画插图直接打回**：窗口代码里用 svg 图形拼东西超过 12 处，记成「自己画插图」（必须修），写完自测时就交回作者。
- **联网取公开数据**（`bench.net`，用户批：只用免费、公开、不要 key 的）：真实地图底图、地名查坐标、天气、汇率、维基百科简介和配图。外壳把名单写进 `data/_net.json`；窗口用 `ctx.net.get(名字, 参数)`（零件库 `net`，本机缓存，联不上返回上次结果并标 `live: false`）；`mapFrame` 有底图时自动用真实瓦片，并能 `onPick` / `focus(i)` 联动。沙箱的 CSP 只放行名单里的网址；质检截图时也放行这些网址，评审才看得到真实地图。会把地名、经纬度发给这些网站。
- **做工具，不做样品**：成品里多了 `ctx.askJson(要求)`，按用户填的条件请助手现场生成一份结构化内容（`bench_ask_json` v1：真实地点、参考价标日期和来源、守用户条件、每条带 id），接口 `POST /api/bench/<id>/ask` 加 `as_json`。拆需求和写窗口的提示词（v4）要求有地方填用户自己的条件、内容跟着变，每个场景（婚礼、生日……）要真的多出内容。
- **分数降了就退回上一版**：每次返工前给每个窗口存一份快照；某组窗口这一轮评审均分比上一轮低 0.3 分以上，就退回上一轮评审看到的版本，下次返工照上一轮的意见、换个改法。

## 调研员与联网自检（2026-10-30，项目室方案第 1 块）

用户 10-30 晚重新说明工作台的定位（任意类型平台、甲方乙方项目制全流程、三位助手协作、每次至少 10 个 GitHub 高质量资料加论文和资讯），并要求「GitHub 的直接使用能力：自己找合适插件或高分项目来学」。方案见 Claude 文档「工作台生成器细化方案」（https://claude.ai/artifact/YSHCetS5xRQipEuo7fT5qw），按推荐全批。第 1 块：
- **调研员**（`core/benchkit/research.py`，配置 `bench.research`）：拆完需求先调研（状态 `researching`）。
  - 一位能联网的助手（`bench_research` v1，按 `research` 活挑人）给 4～6 个英文搜索词，并查最多 `news` 条资讯、视频、发布会、官方博客（只收它实际打开过的 https 链接）。
  - 程序拿搜索词加拆需求的 needs 关键词搜 GitHub：先整句搜，不够 `min_github`（默认 10）个就拆成单个词再搜（匿名限流，最多 8 次）；去掉归档和不到 20 星的，按命中词数和星数排序取前 `max_github` 个，每个按找插件的门槛判「能搬 / 只借思路」。还不够就如实写「只找到 N 个」，不凑数。
  - 论文查 arXiv 和 Semantic Scholar（免费、不要 key），同名去重；dsh 插件集市里对得上的列成「建议给 dsh 装」（这里不装）。
  - 助手给的资讯链接程序再打开一次，打不开的标「没核实」。
  - **学习卡**：星最多的 `learn`（默认 3）个项目，源码钉在提交上只读下载到 `research/learn/<仓库>/`（同找插件：只解压不运行），各交给一位助手读完写学习卡（`bench_learn` v1：是什么、能借什么、别学什么、最值得看的文件；许可证不宽松的只写思路）。dsh 的 `research` 擅长分最高，学习卡多半是它写。
  - 结果存 `research.json` 和 `调研报告.md`；学习卡和前 3 篇论文写进写窗口、返工的「可用资料」（`sources`），写代码的助手照着借。控制室显示 GitHub 表、学习卡、dsh 插件、论文、资讯和视频，以及没找够的说明。
- **联网自检**（`core/benchkit/netcheck.py`，`GET /api/bench/net-check`，控制室右上「联网自检」）：成品要用的公开数据（`bench.net`，网址里的参数用 `probe` 或默认样例）和调研要用的接口（GitHub、arXiv、Semantic Scholar、dsh 插件集市）各发一次只读 GET，显示通不通、多少毫秒，不通的写原因（限流、被代理拦下、连不上）。

## 项目室：甲方乙方全流程（2026-10-30，项目室方案第 2 块）

配置 `bench.project`（`enabled` 开着就走项目室；关掉是原来的一口气做完）。你是甲方，几位助手是乙方，分立项、执行、交付、革新四段，每段停在关口等你（`gate`），**停着的时候不占任何次数**：
- **需求访谈**（`interview`，提示词 `bench_interview` v1）：开工前先问你最多 `max_questions` 个会明显改变成品的问题（给谁用、在哪用、对标哪个产品、不要什么……），能给选项的给选项。你答完（`POST /api/bench/<id>/answer`）或全部跳过才往下做；回答连同原话一起交给后面所有环节（`brief`）。
- **方案书**（`proposal`，`方案书.md`）：拆需求、调研、找插件之后，程序整理验收清单、窗口（标出主视觉）、里程碑（有主视觉时第 1 个只做主视觉）、借鉴的项目和学习卡、建议给 dsh 装的插件。你可以改、删、加自己的要求（底线不能删），写一句补充，点「签字开工」（`POST …/sign`）。签字前一个窗口都不写。
- **里程碑演示**（`m1`…）：按方案书一段一段做，每段写完先自测、截图，停下来给你试用（草稿能直接打开）。你点「通过」进入下一段，或者「提意见」（`POST …/review`，可指定窗口）。意见记成**变更单**（`changes`：c1、c2…），交给负责的窗口返工，改完记「改好了 / 没改成」和助手的说明，再截一次图给你对比「改之前 / 改之后」。`gate_auto_hours` 大于 0 时，里程碑到点没回按通过处理；立项签字和交付验收永远等你。

- **时间线**（`timeline`）：每段交了什么、你做了什么决定，都按时间排在项目室里；叫停或「结束这个项目」随时可以。

## 三位助手协作与 dsh 插件（2026-10-31，项目室方案第 3 块）

配置 `bench.team`（关掉就是原来按分数挑人、各干各的）。超级电脑的几位助手（Codex、Claude Code、dsh）平级，没有主管，每件活照常按擅长、余额、忙闲打分挑人：

- **协作看板**（`team.cards`）：每件活记下谁、当什么角色（拆需求、调研、主案候选、投票、实施、评审、对抗、访谈、革新）、干了什么、成没成。控制室「团队」面板按人分栏，方案会列出各方案、票数、谁投了谁、主案。

## 没过线时你来定、查数据（2026-10-31，项目室方案第 4 块上半）

- **B3 停下来的方式**：做满 `max_rounds` 轮还没过线时，程序整理一份「卡在哪」（`stuck`）：哪几条要求没做到、连续几轮没做到、评审说的原因；质检还有哪些必须修；对抗手的严重问题；评审分的走势；再给几条建议（同一条连续几轮都没做到 → 建议改具体或先删；分数在涨 → 再跑一轮有希望；分数不涨 → 建议改要求或收下）。不在项目室时你可以选「再跑一轮」「改要求再跑一轮」（只能改你的要求，底线不动）或「就这样，收下」（`POST /api/bench/<id>/decide`，`action` 为 `more` / `edit` / `accept`）；在项目室里同样的内容显示在交付验收关口上。
- **方案书写清方案会**：每份方案谁提的、几票、采纳没采纳、投票的人为什么选它，以及从其他方案补进主案的点。
- **C4 查数据**（`lint_data`，写完自测和每轮质检都查）：读每个窗口的 `data/<窗口>.json`，地址为空、「示例 / 占位 / TODO / example.com」这类占位文字、和共用信息矛盾（币种、人数）、不是合法 JSON，直接按窗口打回作者，评审前就拦下；价格、评分这类数字没写来源（`source`）和日期（`date`）的记「建议修」（写在那一条里或文件最外层都算）。
- **C5 自动点一遍**（`poke.js`，质检的第一种屏宽和明暗截完图后跑；`run_check(poke=False)` 可关）：逐个点每个窗口里的按钮、标签、可点的列表项（每个窗口最多 6 个、全页最多 40 个；名字像「删除 / 清空 / 重置 / 导出 / 打印」的不点，弹窗一律取消），比较点之前和之后每个窗口的样子。点了报错 → 必须修；点了页面上什么都没变 → 「点了没反应」；名字像「加入 / 收藏 / 选择 / 保存」的按钮点了只有自己这个窗口变 → 「加入后别处不变」（都按窗口交回作者，后两项是建议修）。写完自测时「点了报错」也当场打回。
- **C6 可执行的验收**（方案书 `bench_plan` v5 起每条要求可带 `probe`：最多 4 步「填 / 选 / 点」，再写点完页面上应出现的字或「要有变化」）：每轮质检后用 `run_probes` 在真浏览器里照着做一遍。做不到的要求直接算没做到（原因写「自动检查：…」），并作为「验收自动检查没过」交回该要求的窗口作者；要现场问 AI 才有结果的步骤记「查不了」，不算作者的错。
