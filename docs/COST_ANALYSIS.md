# 协同模式花费分析（R8）

数据来源：`roundtable estimate`（配置价格 + 公式，不调用模型、没有你本机的历史校准）。题目：「写一份关于固态电池现状的调研报告，包含对比表和结论，约 2000 字」；7 位组员 + 统筹，2026-10-13 的配置。真实花费以 `roundtable show <id> --costs` 为准，下面只是估算。

## 各步骤预估（协同）

| 步骤 | 节电模式 | 全力模式 |
|---|---|---|
| 拆分 / 自荐 / 分配 / 分工讨论 | $0.027 | $0.176 |
| 完成子任务 | $0.116 | $0.407 |
| 交叉审查 | $0.126 | $0.441 |
| 按审查修改 | $0.132 | $0.506 |
| 逐条验收 | $0.004 | $0.039 |
| 统筹合并 | $0.012 | $0.171 |
| 合计 | $0.418 | $1.739 |

最贵的三项是「按审查修改」「交叉审查」「完成子任务」，合计约 78%（全力模式）。R6、R7 新增的分工讨论和逐条验收合计约 $0.017（节电）/ $0.104（全力），约占 4% / 6%。

## 本轮做了什么

1. **短成果少找审查者**：`collab.cross_review`（默认 `short_chars: 400`、`short_reviews: 1`）。成果少于 400 字时只找 1 位审查者，而不是 `reviews_per_answer`（3）位。判断只看成果长度，与作者是谁、用什么模型无关，所有成员同一规则。省下的是「每位审查者读全文」的输入，同时「按审查修改」收到的审查意见也变少。设为 0 即关闭。
2. **按子任务类型设 `max_tokens`**：`collab.kinds.<类型>.step_params`（analyze 4500、prompt / generate 3000、verify / review / factcheck 4000；撰写、写代码、整合仍用 work 的 6000）。只限制最长输出，是**最坏情况的上限**，模型本来就写得短时不会省钱；也不会让输出被截断得更狠，因为长度保护仍会在被截断时提高上限重试。同一类型所有成员相同。
3. 分工讨论和逐条验收都设了上限（最多提 3 条建议、最多退回 3 个子任务、只调整 / 退回一次），保证新增质量步骤的花费有上界。

## 估算怎么看

`roundtable estimate` 事先不知道各份成果有多长，所以交叉审查仍按 3 位审查者估算，是**上界**；实际有多少成果落在 400 字以下，要看题目。

按公式推算：一份成果刚好是短成果时，它的审查读取量降到原来的 1/3（3 位 → 1 位）。若题目里一半的子任务产出是短成果，交叉审查花费约降 1/3，「按审查修改」的输入也随之略降。这是推算，不是实测。

## 2026-10-14 补做：合并时不重复传上游全文

`collab.merge_trim`（默认 `enabled: true`、`excerpt_chars: 600`）。合并时，一份成果如果所属子任务**已经交给下游**，而且下游有成果、没有一份被标记敷衍，就只给统筹看开头约 600 字，并在 `<work>` 上标 `excerpt="完整内容已交给 T3 继续使用"`；`merge/v5` 告诉统筹：以下游成果为准，判断采纳情况时看下游是否用上了它，不要因为只看到开头判为缺失。

保留全文的情况（质量保护）：流水线的终点子任务（没有下游）；下游被标记敷衍；成果本身被标记敷衍或风格未通过；成果本来就不超过 600 字。逐条验收（`accept`）仍看全文。判断只看依赖关系和检查结果，与作者是谁无关。

预估对比（按上面同一道题、同一套公式推算；`roundtable estimate` 仍按全文估，是上界）：统筹合并的输入约 6.6 万 token（全力）/ 3.0 万（节电）。按调研模板 7 人、只有「整合」一个终点计，6 份上游成果改为摘录后：

| | 改动前 | 改动后（推算） |
|---|---|---|
| 统筹合并 · 全力 | $0.288 | 约 $0.171（−41%） |
| 协同合计 · 全力 | $1.739 | 约 $1.622（−7%） |
| 统筹合并 · 节电 | $0.0047 | 约 $0.0016 |
| 协同合计 · 节电 | $0.416 | 约 $0.413（<1%） |

全力模式省得多，是因为统筹用的旗舰模型输入单价高。实际省多少取决于题目拆出几个终点子任务；终点越多省得越少。这是推算，不是实测。

## 2026-10-14 补做：下游向上游提澄清问题（R6）的花费

只在有人提问时多花钱：一次很短的答复调用（`step_params.clarify`，最多 1200 token）+ 提问者再完成一次（同一对话，多出一次完整的「完成子任务」输入）。没人提问时不增加调用。预估里没有单列，因为事先不知道会不会有人问。
