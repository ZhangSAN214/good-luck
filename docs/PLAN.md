# Roundtable 实施计划（v1：核心文字圆桌）

规则：`CLAUDE.md`。长期需求：`docs/REQUIREMENTS_v3.md`。界面样板：`docs/mockup.html`。
每阶段结束：`ruff` + `pytest` 全绿 → git 提交（`phase N: ...`）。

---

## v1 运行时流程

1. **answer**：抽座位 → 各组员独立作答（并发，互不可见）
2. **review**：每个组员评审其他人的匿名答案（乱序、排除自己），输出结构化意见
3. **revise**：各组员看到别人对自己的评审，修订自己的答案
4. **synthesize**：统筹读全部修订稿（匿名、乱序），输出共识 / 分歧 / 最终答案 / 存疑点
5. **reveal**：用户点击后揭晓各代号对应的模型

预算检查在每步开始前进行；顺序在 `config/roundtable.yaml` 的 `pipeline:` 中配置。

## v2 改版（方案待确认，确认前不写代码）

原阶段 11（收尾）顺延到最后，编号改为 20（新增工具能力阶段 15–16、媒体生成阶段 19 后顺延）。v2 完成后 CLAUDE.md 的 §1、§2.3、§3、§4 同步改写。

### 改版要点

**A. 全员上桌 + 成员档位（取代难度路由）**
- 取消"单人快答"和按难度定人数；不再按难度选方案。用户提问时选 **成员档位**：便宜档全员（默认）/ 旗舰档全员 / 自选（勾选模型）。所选范围内**每个可用模型都上桌**。
- "上桌"= 担任组员或统筹。统筹从所选范围内按轮换规则选出、本题不作答（遵守"统筹不兼任组员"）；自选模式可指定统筹。例：便宜档全员 = 5 个组员 + 1 个统筹，6 个模型全部上桌。
- 没有 key / 没有可用渠道的模型无法上桌：执行前在预估卡片上列为"缺席（无可用渠道）"，不算自动减人。调用失败的退出规则不变（剩余组员 < `min_members` 时询问）。
- 规划员与难度判断只保留一个用途：估计答案长度用于花费预估（规则能判断时不调用）。`routing.yaml` 改为：档位选项、统筹规则、预估参数、确认门槛、升级规则。
- **升级**：便宜档全员汇总后仍有未裁定分歧或把握低时，**弹卡片询问**是否用旗舰档全员重做（不自动升级），预估与门槛照常。
- **互评成本控制（不减人）**：每份答案由 `reviews_per_answer`（默认 3）位其他组员评审，分配均衡、排除自评、种子可复现；组员 ≤ 4 人时等同全员互评。
- 代号池扩到 ≥ 启用模型数（甲…癸、子、丑…）。
- 已发布的提示词（如 `answer_quick/v1`）按规则保留，只是不再被引用。

**B. 匿名开关（默认关闭）**
- 提问时选择；存入会话。关闭时界面、API、命令行全程显示真实模型名（每次调用的渠道也直接显示），没有"揭晓"步骤。开启时完全沿用现有机制（代号、遮蔽、揭晓按钮）。
- **发给模型的内容在两种情况下都只用代号、都做身份遮蔽**（避免模型之间因认出对方而偏袒；匿名开关只管给人看的界面）。
- 测试：匿名开启时沿用现有"无泄露"测试；关闭时断言界面显示模型名、发给模型的内容仍无身份。

**C. 文件上传（图片 / PDF / Word / 文本 / 音频）**
- 上传：`POST /api/uploads`（大小、数量、类型上限在 `roundtable.yaml` 的 `uploads`）；文件按内容哈希存在 `data/uploads/`，元数据进新表 `attachments`；文件名只作显示，不参与路径。
- 预处理（每个文件只做一次，结果入库，费用计入本场）：
  - PDF → 提取文字（`pypdf`）；没有文字层（扫描件）时提示用户，v2 不做 OCR。
  - Word（`.docx`，`python-docx`）/ 文本（`.txt`、`.md`、`.csv`，自动识别编码）→ 文字。旧版 `.doc` 不支持。
  - 音频 → 转写成文字：由带 `transcribe` 标签的模型完成（最便宜者优先）。方案：给能直接接收音频的模型（如便宜档里的多模态模型）加 `transcribe` 标签，用"音频 + 转写提示词"的普通对话调用实现，不需要新增仅用于转写的模型；没有可用的转写模型时拒绝上传音频并说明原因。
  - 图片 → 带 `vision` 的模型直接收到原图；同时由最便宜的 `vision` 模型生成一份**文字版**（逐字抄录图中文字 + 公式 + 图表/示意图描述），发给没有 `vision` 的成员。
- 消息格式：`Message.content` 支持"文字 + 图片"多段；三个适配器各自转换（OpenAI 兼容 `image_url` data URI、Anthropic `image` base64、Gemini `inline_data`）；转写用普通对话调用（音频作为消息附件），Provider 的 `transcribe` 方法仍保留为预留接口。
- 中立性：同一步骤提示词正文完全相同，**唯一差别**是附件以图片还是文字版呈现（按 `vision` 标签决定，记录到调用记录）。附件内容放在 `<attachment name="…" type="…">` 标签内，按外部内容处理（防注入）。
- 安全：限大小与页数、只按扩展名 + 文件头双重识别类型、不执行任何内容；上传文件不进日志。

**D. 协同模式（与讨论模式二选一，提问时选）**
- 讨论模式 = 现有流程：作答 → 互评 → 修订 → 汇总。
- 协同模式 pipeline：`decompose → volunteer → assign → work → cross_review → rework → merge`
  1. **decompose**（统筹，JSON）：拆成子任务（标题、要求、验收标准、建议能力标签、依赖）。
  2. **volunteer**（全体成员并发，JSON）：对每个子任务表态（想做 / 可以做 / 不适合）+ 擅长什么、为什么。
  3. **assign**（统筹，JSON）：按自荐和能力标签分配；**代码校验**每人至少一块、每块至少一人、负载均衡，不合格时重试一次，仍不行由代码按自荐 + 标签补齐。子任务少于人数时，由多人**各自独立完成同一子任务**（合并时择优或取长补短）。
  4. **work**（并发）：每人完成自己的子任务（只看题目、附件、自己的子任务和依赖子任务的结果；依赖未完成的子任务分批执行）。
  5. **cross_review**：每份成果由非作者评审（复用互评的质量规则和"不评自己"的分配）。
  6. **rework**：作者按有效评审修改（同讨论模式的修订，没有有效评审则沿用）。
  7. **merge**（统筹，JSON + 正文）：合并成完整成果，并逐个子任务标注采纳情况（全部 / 部分 / 未采纳 + 原因）。
- 协同模式也有升级卡片（合并结果把握低时询问是否用旗舰档重做）。

**E. 防偷懒与贡献记录**
- **实质内容检查**（代码规则，`roundtable.yaml` 的 `effort_check`，按步骤配置）：字数下限（相对预估长度）、拒答 / 空话短语、只复述题目、与他人产出高度重复（疑似照抄）、JSON 关键字段为空。互评沿用现有空泛评审规则。
- 不合格 → 附上原因**打回重做一次**（新提示词角色 `redo`）；仍不合格 → 该产出标记**"敷衍"**（仍保留，参与汇总时注明），面板与座位上显示标记。
- **贡献记录**（新表 `contributions`，按模型 id 记，匿名时也照常记录，揭晓前不对外显示模型）：
  - 被采纳的内容：汇总 / 合并输出里标注每条共识、最终答案要点、子任务成果来自哪些代号（`synthesize/v3`、`merge/v1` 增加 `adopted_from`）。
  - 指出的有效问题：有效评审的问题数；作者在修订中**明确采纳**的问题数（`revise/v2` 的回应改为逐条"采纳 / 不采纳 + 理由"，代码解析）。
  - 自荐被采纳、子任务被采纳、被标记敷衍次数、重做次数。
- 面板新增"贡献"标签：本场每人一行；另有跨会话的历史统计（`GET /api/contributions`），v2 只积累和展示，**不参与分工**（以后再用）。

**F. 预算与预估**
- 预算、门槛、80% 提醒、暂停规则不变。全员上桌后单题花费明显增加：提问时（提交前）即调用 `POST /api/estimate` 实时显示三种档位 × 当前模式的预计花费、各步骤明细和上桌名单（匿名开启时只显示人数），超过门槛的标红；提交后超门槛仍弹确认卡片。
- 粗略量级（按当前配置价格估算，实际以预估接口为准）：讨论模式便宜档全员约 $0.05–0.15 / 题，旗舰档全员约 $0.4–0.8 / 题；协同模式略高。每日 $3 上限约够旗舰档 4–6 题。

**G. 工具能力（已确认：全部按建议；另加图像生成工具，扩展成员能产出的东西：代码、图表、插图、Word / Excel / PPT / PDF 等）**

成员在作答过程中可以申请使用工具：运行 Python、生成文件、联网搜索。工具对同一步骤的所有成员完全相同（同样的工具、限额和说明），只看配置，不看是哪个模型。

- **调用方式：文字协议**（推荐，所有模型、所有渠道一致，Fake 可测）。成员在输出中写 `<tool_call>{"tool": "python", ...}</tool_call>`；代码解析并执行，把结果放进 `<tool_result>` 追加到同一对话，再调用一次；不再申请工具的那次输出就是最终结果。工具说明放在新提示词 `tools/v1`（接在该步骤系统提示之后，与 redo 相同的做法），现有提示词不改。
  - 不用各家原生的 function calling：三个适配器格式不同，聚合平台上部分模型不支持，难以保证"同一步骤所有成员同样对待"。代价是偶尔格式写错——写错就当作最终结果处理，不会卡住。
- **哪些步骤能用什么**（`roundtable.yaml` 的 `tools.by_step`，默认值）：

  | 步骤 | python | 生成文件 | 搜索 |
  |---|---|---|---|
  | 作答 / 修订（讨论）、完成子任务 / 修改（协同） | ✓ | ✓ | ✓ |
  | 互评 / 交叉审查（用来核算、核对来源） | ✓ |  | ✓ |
  | 合并（统筹整理交付文件） | ✓ | ✓ |  |
  | 规划、拆分、自荐、分配、汇总 |  |  |  |

- **限额**（全部可配置）：每次作答最多 `max_rounds` 轮工具调用（默认 6）；python 每步最多运行 `max_runs`（默认 3，出错改了再跑也算一次）、每次限时 30 秒、内存 512 MB；单个文件 10 MB、每场合计 100 MB；每步最多搜索 3 次。超出时告诉成员"额度已用完，请直接给出结果"。

**G1. 代码运行（本地隔离环境）**
- 统一的 `Sandbox` 接口，两种后端（`tools.python.backend`）：
  1. **`wasm`（推荐默认）**：Pyodide（编译成 WebAssembly 的 CPython）跑在 Deno 里。Deno 只授予"读写本次的工作目录 + 读 Pyodide 自身文件"的权限，不给网络、环境变量、子进程权限；WebAssembly 本身也没有系统调用。Windows / macOS / Linux 都能用，不需要 Docker；由 `python scripts/setup_sandbox.py` 一次性下载 Deno 与 Pyodide（含 numpy、pandas、matplotlib、sympy、openpyxl、python-docx 等），之后完全离线。限制：只能用 Pyodide 带的包，速度比原生慢。
  2. **`docker`（可选）**：仓库附带 `sandbox/Dockerfile`（原生 CPython + 上述包），用 `--network none`、只读根目录、`--memory`、`--pids-limit`、`--cap-drop ALL`、非 root 用户运行，只挂载工作目录。需要本机装好 Docker / Podman。
  - **没有可用后端时 python 工具直接关闭**（提示词里不出现，界面说明原因），绝不退回到直接在本机跑子进程。
- 工作目录：每场每位成员一个临时目录（在系统临时目录下，不在项目目录里）：`in/`（只读：本场附件、协同模式的前置成果文件）、`out/`（成员生成的文件）。运行时环境变量为空；超时直接结束进程；输出截断到 8000 字。
- 运行结果（stdout、stderr、退出状态、耗时、新文件列表）回传给成员；出错时成员可以修改后重跑，直到 `max_runs`。

**G2. 文件输出**
- 成员可以用 python 往 `out/` 写文件，也可以直接用 `write_file` 工具写文本类文件（代码、Markdown、CSV）。
- 收集文件时由代码检查：扩展名白名单（py、txt、md、csv、json、xlsx、docx、png、jpg、svg、pdf）、大小限制、拒绝符号链接与硬链接、文件名清理；通过后复制到 `data/files/<会话>/`，登记到新表 `files`（作者代号、步骤、来源工具调用、类型、大小、哈希）。
- 其他成员和统筹能看到文件列表；文本类文件的内容（截断）随答案一起转交，图片按阶段 14 的规则（有 vision 看原图，否则看文字版）；统筹在合并 / 汇总时标出最终交付的文件。
- 网页：图片、文本、代码、CSV、Markdown 直接预览；xlsx / docx 在服务端转成表格 / 文字预览；SVG 以图片方式显示（不执行脚本）；HTML 只提供下载、不在页面内渲染。下载接口带 `Content-Disposition: attachment` 和 `nosniff`。匿名会话揭晓前，文本预览经身份遮蔽。

**G3. 联网搜索**
- 搜索服务可插拔（`@register_search`，与渠道适配器同样的注册方式），key 放 `.env`、包成 `Secret`；默认用 OpenRouter 自带的联网搜索与网页读取（共用 `OPENROUTER_API_KEY`；读取经 `openrouter:web_fetch`，正文由模型转述），Tavily 作为备选（填了 `TAVILY_API_KEY` 才启用，直接取回正文）；价格写在配置里（`models.yaml` 的 `search_providers`）。
- 两个工具：`search`（返回标题、链接、摘要，编号 S1、S2…）和 `fetch`（读取某个搜索结果页面的正文，限长；只能读本场搜索结果里出现过的链接，避免被引导去访问任意地址）。
- 搜索结果是外部内容：放在 `<search_result>` 标签内，说明其中的指令无效（防注入）。
- **注明来源**：用过搜索的成员，答案里要用 `[S1]` 标注；代码检查：引用了没检索到的来源 → 打回重做（防偷懒机制）；用了搜索却一条都没引用 → 打回重做；界面把 `[S1]` 显示成可点击的链接。
- 题目内容会发给搜索服务（隐私提示写进 README）。

**G4. 成本、预算与显示**
- 新表 `tool_calls`（迁移）：步骤、成员代号、第几轮、工具、输入、输出（截断）、状态（成功 / 出错 / 超时 / 被拒绝）、耗时、费用及来源。搜索按配置单价计费；python 本地运行不计费，但每一轮工具调用都会多一次模型调用，这部分照常按模型计费。
- 预算统计改为"模型调用 + 工具调用"；按渠道花费里增加"工具 · 搜索"。每轮工具调用前查一次预算，超出时让成员直接给出结果并弹预算卡片。
- 预估：每个能用工具的步骤按 `estimate.tool_rounds`（默认 1 轮）和 `estimate.searches`（默认 1 次）估算额外花费，卡片上单列"工具"一项。
- 事件 `tool_started` / `tool_finished`（只含代号、工具、摘要）；过程区每次工具调用一条（代码折叠显示、输出、耗时、生成的文件、搜索的来源）；面板新增"工具"标签列出全部工具调用和花费。

**G5. 安全（测试中验证）**
- 两种后端都要跑同一组"越权"测试，全部必须失败或被拦下：读项目根目录的 `.env`（绝对路径和相对路径）、读项目里的源码、读系统文件（`/etc/passwd`、`C:\Windows\win.ini`）、列出用户主目录、读环境变量里的 key、写工作目录之外、连接本机端口和外网、启动子进程、在 `out/` 里放指向 `.env` 的符号链接（收集时必须拒绝）、死循环（超时被结束）、占用过多内存、超长输出（被截断）。
- 另有始终运行的静态测试：沙箱启动参数里没有网络权限、只授权工作目录、环境变量为空；工作目录不在项目目录内；工具结果、日志、数据库里没有 key。
- 本机没有对应后端时这组测试自动跳过（与 Playwright 测试相同）；提交前我会在开发环境里装好后端，确保它们真的跑过。

**H. 媒体生成（已确认，阶段 19，排在阶段 18 之后）**

一、接入的模型（全部走 OpenRouter，作为工具使用，不上桌、不占座位）
1. 图片：保留现有的 Gemini 图像模型，再加一个便宜档（如 GPT Image 1 Mini）和一个高质量档（如 GPT Image 2）
2. 语音转文字：Whisper 系列，用于上传音频的转写
3. 文字转语音：选一个性价比高的 TTS 模型
4. 视频：选一个便宜档（如 Seedance Mini 或 Wan）和一个高质量档（如 Veo 3.1 或 Kling Pro）
5. 音乐/音效：先预留接口，暂不启用

具体 ID 和价格以 OpenRouter 为准，并扩展 check_models.py，让它也能核对媒体模型（视频模型可以用 /api/v1/videos/models 接口查询）。

二、配置
1. models.yaml 增加能力标签：image_gen、image_edit、tts、stt、video_gen、music_gen，以及档位 budget/flagship
2. 计价单位按模型区分：按张、按秒、按分钟、按字符或按 token，预估和记账都按各自的单位
3. 媒体模型的选择和文字模型一样：只看能力标签和档位，同档内随机，不写死品牌

三、流程
1. 讨论模式：成员先讨论并写出生成提示词 → 生成 → 有 vision 能力的成员评审结果（把图片、视频截帧真正发给他们）→ 不满意就修改提示词重新生成，最多 N 轮（可配置）
2. 协同模式：拆分时可以把子任务标记为图片、语音或视频类型，由负责的成员写提示词并调用对应的生成模型，再交叉审查
3. 视频是异步任务：提交 → 轮询 → 下载；要支持超时、失败重试、中途暂停后恢复

四、花费与确认
1. 执行前预估媒体生成的费用，单独列出
2. 视频每次生成前都必须让我确认；图片和语音超过单题门槛时才确认
3. 媒体费用计入每日和每月预算

五、网页显示
1. 图片直接显示，音频和视频可以在页面里播放，都可以下载
2. 显示每次生成用的模型、提示词、花费和第几轮

六、测试
用 Fake 媒体模型覆盖：生成、评审、重新生成、视频异步轮询和超时、预算拦截、视频确认卡片、暂停后恢复。

> **实现说明（阶段 19）**：与方案一致，另有这些取舍：① 语音只生成一次、不做评审循环（没有可评审的画面；转写回读校验留待以后）；② 讨论模式的输出类型在提问时选择，协同模式由统筹拆分时决定（所以协同模式拒绝「输出类型」参数，只接受媒体档位）；③ 协同模式的视频按「批」确认（`work` 每个依赖层一次、`rework` 一次），讨论模式按轮确认；④ 音乐 / 音效只在标签词表里预留；⑤ 配置里的媒体模型 ID 与价格尚未用 `check_models.py` 核对（本环境无法访问 OpenRouter），媒体价格只列出远端 pricing 供人工核对。
>
> 与现有实现的衔接（实现时注意，不改变以上方案）：阶段 15 的 `generate_image` 工具与 `seat: false` 工具模型会并入这里的图片档位选择；阶段 14 的音频转写目前用带 `transcribe` 标签的多模态对话模型完成，引入 `stt`（Whisper）后改为优先用 `stt` 模型，旧标签保留兼容；成员生成的图片已经会发给有 vision 的成员（阶段 16.1），视频截帧沿用同一机制。

## v2.1 协同流水线与参考图风格（方案待确认，确认前不写代码）

起因：一次真实的协同模式运行（参考"人物介绍"四格卡做二创）暴露两个严重问题。

**问题 1**：上传的参考图没有被遵循——五个成员各画各的、风格互不相同，也没有做成四格卡。原因（已核对代码）：① 参考图只以附件形式进入成员的对话，没有任何环节把它提炼成"全体共享的风格规范"；② 画图模型只收到一段文字描述（`MediaService.generate` / `generate_image` 工具都只传提示词，参考图没有传给画图模型）；③ 审查者看到的是生成图，但不拿参考图对照，也没有"风格不合格就退回重画"的环节。

**问题 2**：协同模式变成"各做各的"。原因：`decompose` 接受只有一个子任务的拆分，`fallback_decomposition()` 也是"完成整道题"；子任务少于人数时按现有规则"多人各自独立完成同一块"，于是五个人把整道题各做了一遍；子任务没有类型，分配只看自荐和标签重合，没有"上游产出交给下游"的约束。

### A. 协同流水线（阶段 21）

**A1 子任务类型与交接**
- `Subtask` 新增 `kind`（类型）和 `handoffs`（上游交接清单：从哪个子任务、交什么）。类型词表与规则放在 `roundtable.yaml` 的 `collab.kinds`，不写进代码：

  | 类型 | 含义 | 偏好的能力标签 | 规则 |
  |---|---|---|---|
  | `analyze` 分析 | 读参考图 / 材料，提炼要点、规范 | 题目带图片时 `vision`，否则 `research` | 可多人并行 |
  | `write` 撰写 | 设定、文案、正文 | `writing` | 可多人并行 |
  | `prompt` 写提示词 | 把设定写成交给生成模型的提示词 | `writing`、`design` | 单人 |
  | `generate` 执行生成 | 带参考图调用生成模型（需要有可用的媒体模型） | — | 单人；必须依赖某个 `prompt` |
  | `review` 审查 | 对照要求 / 参考图检查上游成果 | `vision` | 可多人；必须依赖非 `review` 的成果 |
  | `assemble` 整合排版 | 用 Python 拼接、排版成最终文件 | `code` | 单人；至少依赖 2 个上游，能用 python 工具 |

- 拆分 JSON 里每个子任务多两项：`kind`，以及 `depends_on` 的每项可写成 `{"id": "T1", "gives": "风格规范"}`（仍兼容纯字符串，缺 `gives` 时用上游子任务的标题）。
- 提示词：`decompose/v4`（新版本文件，`v3` 不改）。说明类型词表、"必须是流水线：每个子任务的产出交给下游继续做"、"禁止把整道题作为一个子任务"、可用的媒体种类。

**A2 拆分校验（代码判定，规则在 `collab.pipeline`）**
成员数 ≥ `pipeline.min_members`（默认 2）时，拆分必须同时满足，否则视为不合格：
1. 子任务数 ≥ `min(成员数, pipeline.min_subtasks_cap)`（默认上限 4），且不是"整题"：只有一个子任务；或某个子任务的标题 / 要求含"完成整道题""全部要求"等短语（`pipeline.whole_task_phrases`）；或与题目相似度 ≥ 阈值（复用 `similarity()`）。
2. 依赖图是连通的（没有孤立的子任务），且至少有两层（有上下游）。
3. 类型不全相同：不同类型数 ≥ `min(3, 子任务数)`。
4. 类型规则：`generate` 依赖 `prompt`、`review` 依赖非 `review` 的成果、`assemble` 至少两个上游；`generate` 只在有可用媒体模型时允许。
- 不合格 → 把具体问题列给统筹重拆一次（和现有的分配重试同一套做法）；仍不合格 → **按模板自动生成流水线**（A3）。成员数不足 2 时不适用本节（保持现有行为）。

**A3 模板兜底**（`collab.templates`，配置驱动，不写进代码）
- 按题目性质选模板：有图片附件且有可用的画图模型 →"带参考图的创作"；有画图模型无图片 →"无参考图的创作"；否则 →"文档"。
- "带参考图的创作"模板 = 你期望的流程：分析参考图（风格规范）→ 撰写角色设定和文案 → 写画图提示词 → 带参考图生成 → 对照参考图审查 → 用 Python 拼成成品。"文档"模板：分析要点 → 起草 → 审查 → 整合。
- 成员少于模板长度时按 `merge_order` 合并相邻子任务；成员多于子任务数时，多出的人作为 `analyze / write / review` 的并行负责人（只有这三类允许多人）。

**A4 按能力分配、回避冲突**
- `repair_assignment()` 的"合适程度"加入类型偏好标签（权重大于自荐）；统筹的分配仍先试一次，代码校验不合格再补齐。
- 硬性约束（代码校验，`assignment_conflicts()`）：
  - `review` 的负责人不能是它上游任何 `prompt` 子任务的负责人（即"同一个人不能既写提示词又审查自己提示词生成的结果"）；
  - 单人类型（`prompt / generate / assemble`）只有一个负责人；
  - 成员只有两个时无法同时满足的约束按"先放宽对 `write / generate` 的回避，永不放宽 `prompt` 的回避"的顺序放宽，并把放宽写进 `repaired` 提示用户。
- 取消"子任务少于人数时多人各自独立完成同一块"在流水线模式下的使用（仍保留给成员数 < 2 之外的旧路径不再触发）。

**A5 上游产出传给下游**
- 现有：`<dependency>` 块已把上游文本和文件列表传给下游。新增：每个块标明交接内容（`gives`）和上游负责人；上游生成的**图片 / 视频截帧**按 `vision` 规则随附给下游（沿用 16.1 的机制）。
- **上游文件进入下游的工作目录**：`Workspace` 的 `in/` 目前只放用户附件；改为同时放入依赖链上游子任务生成的文件（最新版本）。这样 `assemble` 的负责人可以直接用 Python 把图片拼成四格卡。`tools/v5` 说明 `in/` 里有上游交来的文件。
- `generate`：负责人先做一次短调用确认 / 微调上游提示词（输出最终提示词，不得改动风格规范），然后由代码调用 `MediaService` 生成（阶段 22 起带参考图），生成物登记在负责人名下并交给下游。
- 各类型各有简短的工作提示词：`work_analyze`、`work_write`、`work_prompt`（由 `work_media` 演进）、`work_generate`、`work_review`、`work_assemble`（均为新角色 / 新版本，`work/v1` 不改，旧流程不受影响）。

**A6 交接链界面**
- 新产出类型 `handoff`：下游子任务开始时记录 `{从: 子任务 / 负责人, 到: 子任务 / 负责人, 内容: gives, 文件}`；事件 `handoff`（只含代号）。
- "分工"面板新增交接链图：按依赖分层从左到右，节点 = 子任务（类型、标题、负责人、状态），连线上写交接内容并显示缩略图 / 文件；过程区在每个子任务开始处显示"组员乙 把〈风格规范〉交给 组员丙"。匿名揭晓前只显示代号。
- 命令行 `show` 增加"交接链"一段。

**A 的测试**：整题单任务被判不合格并重拆；重拆仍不合格走模板，且模板在 2 / 3 / 5 / 8 个成员时都满足 A2；连通性、类型规则各自的反例；`review` 不会分给上游提示词的作者（含只有 2 个成员的放宽路径）；单人类型不出现多个负责人；上游文本 + 图片传到下游（vision 成员收到图片，其他只收到名称）；上游文件出现在下游工作目录 `in/` 并能被 python 读取（有沙箱时）；交接记录与事件；中断恢复不重复调用；匿名视图无身份；旧的协同流程（成员数不足 2 的路径）行为不变。

### B. 参考图风格与图生图（阶段 22）

**B1 风格规范提取（新步骤 `style`，讨论 / 协同两种模式共用）**
- 触发条件：会话带图片附件，且会用到画图（讨论模式选了图片输出，或协同模式且有可用的画图模型）。放在 `decompose`（协同）或 `answer`（讨论）之前，作为流水线的第一站（交接链里显示为第 0 个节点）。
- 做法：带 `vision` 标签的在场成员（最多 `style.reviewers` 位，默认 2）各自独立看原图，按固定结构输出（画风、配色（色值）、线条、构图、版式（格数、边框、比例）、字体与文字排布、禁忌）；统筹合并成一份**风格规范**和 6–10 条可检查的"风格清单"。存为 `outputs` 的 `style_spec`，恢复时不重复调用。
- 没有 vision 成员时：用图片的文字版（阶段 14 已有）代替，并提示"风格规范来自文字描述，可能不准"。
- 新提示词：`style_extract/v1`、`style_merge/v1`、`style_guide/v1`（把风格规范放进后续每次调用，接在系统提示后，和 `attachments` 同样的做法；同一步骤所有成员相同）。

**B2 参考图真正传给画图模型**
- `MediaService.generate()` 新增 `references`（原图字节，来自图片附件，最多 `media.references.max` 张、每张不超过 `max_mb`）。提供者的 `generate_image(..., images=)` 已存在，OpenRouter 走对话接口时作为 `image_url` 传入。
- 选模型：带参考图时优先选带 `image_edit` 标签（支持图生图 / 参考图）的模型（`prefer_tags`，和语音按语言选同一机制）；没有这样的模型时退回只传文字，并在界面和告警里明确写出"没有支持参考图的画图模型，只能按文字风格规范生成"。
- 提示词里仍写入风格规范（双保险）；`media_jobs` 新增 `references` 列（迁移 9），界面的生成卡片显示"参考图 N 张"。
- 讨论模式的 `media` 步骤和协同模式的 `generate` 子任务都走这条路径；`generate_image` 工具同样支持（成员申请时可附参考图编号）。
- `check_models.py` 增加核对：带 `image_edit` / `vision` 标签的模型，远端 `input_modalities` 必须含 `image`。

**B3 对照参考图审查，不合格退回重画**
- 讨论模式：`media_review/v2` 给评审者随附参考图 + 风格清单，逐条判定"符合 / 不符合"，任意一条不符合即 `satisfied=false`；统筹的改写意见必须针对不符合的条目（沿用现有 生成 → 评审 → 重新生成 循环，轮数仍受 `media.max_rounds` 限制）。
- 协同模式：`cross_review` 对媒体成果同样带参考图和清单；新增步骤 `style_gate`（放在 `rework` 之后、`merge` 之前，没有媒体成果时跳过）：非作者的 `vision` 成员对每份媒体成果做通过 / 不通过判定，不通过则带着意见重新生成，最多 `media.style_retries` 次（默认 2）；仍不通过时保留最后一版并在成果上标"风格未通过"，合并时统筹可见。
- 每次重画仍受预算与视频确认约束；图片超过单题门槛时的确认规则不变。

**B4 界面**
- 上传的图片在提问区标注"风格参考"（可取消勾选，默认勾选；取消的图片只作为普通附件）。
- 过程区在附件处理之后显示"风格规范"卡片（可折叠），生成卡片显示参考图缩略图和风格审查结果（逐条清单的通过 / 不通过）。

**B 的测试**：有图片附件时先出风格规范，没有时不触发；没有 vision 成员时用文字版并告警；风格规范进入后续每次调用且同一步骤所有成员相同；参考图字节出现在发给画图模型的请求里（Fake 提供者记录）；带参考图时选 `image_edit` 模型、没有时退回文字并告警；`media_jobs.references` 记录；讨论模式评审不通过 → 重画，通过则停；协同模式 `style_gate` 的重画次数上限与"风格未通过"标记；匿名时风格规范与卡片不含模型身份；`check_models` 的输入模态核对；旧流程（无图片附件）不受影响。

### 需要你拍板的地方（我的建议在前）

1. **风格规范提取做成系统步骤**（建议）还是做成协同模式里的第一个子任务？系统步骤两种模式都能用、每次必做；子任务更"协作"但讨论模式没法用，且可能被统筹漏拆。
2. **流水线模式下单人类型不允许多人重复做**（建议）。代价：成员比子任务多时，多出的人只能当并行的分析 / 撰写 / 审查者，不能再"各做一份整题"。
3. **`generate` 子任务让负责人先做一次短调用确认提示词**（建议，多一次便宜调用，体现"一方写提示词、另一方执行"）；还是纯代码直接用上游提示词生成（省一次调用）？
4. **哪个画图模型支持参考图**：目前配置里只有 `gemini-3.1-flash-image`、`gpt-image-1-mini`、`gpt-image-2`。我不确定它们在 OpenRouter 上是否都接受图片输入——我会在实现时给它们加 `image_edit` 标签并让 `check_models.py` 用远端的 `input_modalities` 核对；你本机跑一次就能知道哪些标错了。
5. **风格审查仍是模型主观判断**，没有图像相似度的自动指标；`style_retries` 默认 2、上限由你定。
6. 成员只有两个时，`review` 与 `generate` 的负责人可能是同一人（只保证"写提示词的人不审查结果"）；是否可以接受？
7. 模板里的子任务文案放在 `config/roundtable.yaml`（可由你改）；只提供三个模板（带参考图创作 / 无参考图创作 / 文档），其他题型走文档模板，可以吗？

5. 单个组员调用失败（所有渠道都失败后）：记录错误，该组员退出后续步骤；剩余组员 < 2 时暂停问用户
6. 修订 1 轮
7. 统筹轮换规则：从非组员的可用模型中按会话轮换
