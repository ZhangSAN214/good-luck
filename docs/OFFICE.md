# 办公室模式（O1～O5）

> 2026-10-19 起草。来源：用户在「为什么超预算、又笨又慢」线程中的设想——**像真正的办公室，既能讨论也能分工，AI 都是员工，token 就是工资；由 ChatGPT 和 Claude 主导统筹**。
> 2026-10-19 用户确认：第 8 节全部按默认（括号里的默认值即为决定），同意第 6 节的规则修改（只在办公室模式生效）。路线图编号 R17。
> 进度：**O1～O5 全部完成**（名册、工资单、单件上限；经理分诊 + 单人办，现为默认方式；开会；项目分工；绩效）。

## 1. 为什么要改

现在的默认流程更像一间考场，而不是办公室：每道题全档位 7 人各写一遍，再互评、修订，最后由一位随机统筹以低思考强度把 7 份揉成一份。结果是花 7 份钱、等 4 轮以上，拿到的是折中答案（原因分析：项目资料 `分析/超预算与慢笨原因.md`）。

办公室的做法相反：**经理先判断活有多大，小事一个人办，大事才开会或分工；按能力和工资派活；会议短而有目的；工资看得见；有绩效记录。**

## 2. 角色

| 角色 | 谁 | 职责 |
|---|---|---|
| 经理 | ChatGPT、Claude 的旗舰模型（用户指定，可在名册里改） | 收件、判断怎么办、派活、开会拍板、验收、写最终交付 |
| 员工 | 名册里其余在岗模型（节电档 + 旗舰档都可） | 按派到的活干：查资料、写初稿、写代码、核对、提意见 |
| 老板 | 用户 | 定工资预算；超预算或重大决定时拍板；随时插话 |

- **两位经理怎么分工**（默认，待用户确认）：每件事轮流由一位当「主办经理」，另一位只在「项目」级任务的最终验收时当「复核经理」。小事不惊动第二位经理。
- 经理也可以亲自干活，但默认只做判断、拍板和最终交付，干活优先派给工资低的员工。
- 指定经理写在配置里（`models.yaml` 每个模型的 `office_role: manager`，默认 `staff`；O1 已实现），**代码不写任何模型名分支**，换经理只改配置。`routing.yaml` 仍只引用档位和标签。

## 3. 三种办事方式（经理分诊时选，老板可改）

1. **单人办**（大多数日常问题）：经理派给最合适的一位员工 → 员工完成 → 经理快速过目（有问题退回一次）→ 交付。调用 3 次左右。
2. **开会**（有争议、需要多角度、重要决定）：经理点名 2～3 位相关员工 → 每人发言一次（可以看到前面的人说了什么，像真实会议，而不是背对背各写一份）→ 经理拍板并写会议纪要和结论。
3. **项目分工**（长报告、作品、代码等）：沿用现有协同流水线（拆分 → 派活 → 交接 → 审查 → 返工 → 验收 → 合并），但
   - 只派需要的人数，不再强制全员上桌；
   - 审查只对关键成果做，不是每份都 3 人互审；
   - 最终合并由主办经理以中等以上思考强度完成，复核经理验收。

经理分诊时同时给出**预算单**（预计用谁、多少工资）；在老板设的单件上限内直接开工，超出才弹卡片。

## 4. 工资（token = 工资）

- **名册**显示每位员工的「时薪」（输入 / 输出每百万 token 价格）、擅长（能力标签）、本月已领工资。
- 每件事结束出一张**工资单**：谁干了什么、各花多少、经理花多少、搜索等外包费用多少。
- **部门预算** = 现有的月 / 日预算，改叫「本月工资预算」；单件上限替代现在的 $0.30 门槛，按办事方式分别设（如单人办 $0.05、开会 $0.15、项目 $0.80，待用户定）。
- 联网搜索只在需要查资料的活里给，不再默认人人每步都搜（这一项也是现在花费和慢的大头）。

## 5. 绩效

- 每位员工按活的类型记：被经理退回的次数、验收通过率、平均工资花费、平均用时。
- 名册上可看；经理派活时作为参考（同等条件下优先表现好、工资低的）。
- 只用于派活和展示，老板可一键清零。

## 6. 和现有规则的冲突（需要老板拍板才能改）

| 现有规则 | 办公室模式要怎么改 |
|---|---|
| 规则 9：所选档位全员上桌；统筹在场内均匀随机；无品牌偏好 | 办公室模式例外：经理由老板指定，员工按需派，不全员上桌 |
| 规则 9：分配只看档位、标签和价格 | 办公室模式加上「绩效」作参考 |
| 规则 2/7：匿名 | 办公室模式默认实名（昵称），匿名只留给旧的讨论模式 |
| 规则 1：同一步骤所有成员提示词、参数相同 | **保留**：同一类活的提示词和参数对所有员工相同，经理之间也相同 |
| 规则 4、6：不自评；统筹不兼任组员 | **保留**：员工的成果不让本人审；经理亲自干的活由另一位经理复核 |

旧的「讨论」「协同」「头脑风暴」保留为可选模式（相当于「全员大会」），默认改为办公室模式。

## 7. 分步计划（每步做完可单独试用）

| 步 | 内容 | 预估 |
|---|---|---|
| O1 | 名册与工资：配置里的经理 / 员工角色、时薪显示、工资单、单件上限；规则文档与测试按第 6 节修改 | 半天～1 天 |
| O2 | 经理分诊 + 单人办（含经理过目、退回一次）；搜索只在需要时给 | 1～1.5 天 |
| O3 | 开会：点名 2～3 人、顺序发言、经理拍板与会议纪要 | 1 天 |
| O4 | 项目分工：协同流水线改为按需派人、关键审查、经理合并与复核 | 1～1.5 天 |
| O5 | 绩效记录与名册页面，派活参考绩效 | 1 天 |

预期效果（推算，未实测）：日常问题从现在的约 $0.27～0.36 / 4 轮以上，降到约 $0.02～0.05 / 2～3 次调用；最终答案由强模型认真写，质量明显好于现在的折中汇总。

## 8. 老板的决定（2026-10-19，全部按默认）

1. 两位经理：轮流主办（默认）／固定一位主办另一位复核／每件事两位都参与？
2. 经理能不能自己干活（默认：只判断和交付，干活派给员工）？
3. 绩效参与派活吗（默认：参与，作参考）？
4. 单件上限的三个数字和月工资预算。
5. 办公室模式默认实名还是匿名（默认：实名，显示昵称）？
6. 第 6 节的规则修改是否同意。

## 9. O1 已实现的内容

- 配置：`models.yaml` 的 `office_role`（`manager` / `staff`，经理必须 `seat: true`）；`roundtable.yaml` 的 `office.task_caps_usd`（单人办 / 开会 / 项目）与 `office.manager_strategy`（`rotate`）。
- 核心：`core/office/roster.py`（名册：经理在前，员工按工资标准从高到低；本月已领工资来自 `Repository.spent_by_model()`）、`core/office/payroll.py`（工资单：按组员代号、按桌的统筹、外包分别汇总；基于 `session_view()`，匿名揭晓前不含模型 id）。
- 接口：`GET /api/office`（名册、单件上限、本月工资预算）、`GET /api/sessions/{id}/payslip`。
- 网页：面板新增「员工」页；「用量」页显示本场工资单。
- O1 只做展示，不改变任何派活逻辑；单件上限在 O2 起生效。

## 10. O2 已实现的内容（经理分诊 + 单人办）

- 流程：`roundtable.yaml` 的 `office_pipeline: [intake, handle, check, reveal]`，是网页和命令行的**默认方式**（网页记住每位使用者上次选的方式）。
  - `intake`（经理）：看题目和在岗员工名单（称呼、擅长、档位、工资标准），输出办事方式、派给谁、要不要查资料、工作说明。经理的输出不能用或派给了名单外的人时，代码按规则派：标签对口（带图片的题需要 vision）的员工里预计成本最低的一位。经理建议开会 / 项目分工时，O2 先按单人办处理并注明。
  - `handle`（一位员工）：按工作说明办理；**只有经理判断需要查资料时才提供 search / fetch**。调用失败时按规则改派一次。
  - `check`（经理）：过目，通过就交付；退回时员工按意见改一次（`fix`），交付修改版。过目失败时直接交付并注明。
- 阵容：经理只来自 `office_role: manager`（多位时按统筹轮换规则轮流主办，不受档位限制）；员工是所选档位其余能上桌的模型，全部在岗，但只派一位干活。
- 花费：确认门槛用 `office.task_caps_usd.single`（$0.05）；预估按最贵的一位员工算办理。节电档一件事约 $0.05，讨论模式同题约 $0.37。
- 提示词：`office_intake`、`office_handle`、`office_check`、`office_fix`（v1）；步骤参数见 `step_params`。
- 显示：网页「分诊派活 / 办理 / 经理过目 / 按意见修改」与「交付」卡片；命令行【经理分诊】【经理过目】【交付】。

## 11. 夜间轮新增（2026-10-20）

- **人才市场**（`core/catalog.py`）：对照聚合渠道 `GET /models` 的公开列表，找出价格变动、下架、同系列（路由 id 的前缀）更新的模型，按输出价格对照各档位已配置模型的价格区间建议档位、可替换谁。只看路由 id、档位和价格，不针对具体厂商写分支；**结果只展示，不改 `models.yaml`**，换人 / 改价格要老板确认后再改。缓存在数据库旁边的 `model_candidates.json`（`data/` 不进仓库），超过一天网页自动刷新。
- **公寓楼**（`core/office/apartment.py`）：每个厂商一位住户；作息按浏览器本地时间和住户编号确定（不随机）；进行中会话的座位决定谁在上班（讨论类在会议室，办公室 / 个人作答在办公室）；**匿名未揭晓的会话只计数**。`GET /api/apartment?hour=&weekday=`。
- **群聊**（`core/chat.py`）：成员用 `chat.tier` 档位的模型发言，只回应用户；调用挂在群聊的隐藏会话（`workflow = 'chat'`，不出现在历史列表）上，计入预算和工资。`GET/POST/DELETE /api/chat`。群聊不匿名；工作模式提示词不受影响。

## 12. O3 已实现的内容（开会，2026-10-22）

- 分诊：`office_intake/v2` 让经理在决定开会时用 `attendees` 点名参会员工，`brief` 写会议议题。点名的人不在名单上、看不了图（题目带图片时）、重复或多于 `office.meeting.max_attendees`（3）时剔除；不够 `min_attendees`（2）时按单人办的规则（对口、预计成本最低）补齐并注明；在岗员工不够两位时改单人办。经理不参会发言（规则 6）。
- 卡片（与项目分工共用，键 `office_group:<桌号>`）：开会预计花费（每人发言一次 + 经理拍板，按配置价格公式）超过 `task_caps_usd.meeting`（$0.15）时弹「要不要开会」：开会 / 改单人办 / 停止。预算不够时先弹预算卡片。分诊结果先存库，回复后不再调用经理；回复存为 `office_approval`。
- 开会（`handle` 步骤内）：参会员工按随机顺序（由会话 seed 派生，可复现）各发言一次（`speak`，`office_speak/v1`），后发言的看得到前面的发言，要求先回应再补充、不附和；同一场会所有员工的提示词模板和参数相同。发言调用失败的跳过并注明，全部失败时步骤失败。开会不提供工具。
- 拍板（`decide`，`office_decide/v1`）：经理看全部发言，写「## 结论」（即交付）和「## 会议纪要」（每人观点、分歧、采纳理由），不按人数投票。经理调用失败时把各位的发言原样交付并注明。
- 过目：开会的结论是经理自己拍板的，`check` 跳过（规则 4：不自审）。
- 花费：开会前的总预估仍按单人办算；确认开会后，开会预估计入超支保护，不会在跳过的「过目」前误弹超支卡片。
- 显示：网页「开会」阶段（参会名单、议题、各人发言、交付卡片「N 位员工开会 · 经理拍板」）；命令行【经理分诊】开会、`--details` 列出各人发言、【交付】。

## 13. O4 已实现的内容（项目分工，2026-10-22）

- 分诊：`office_intake/v3` 让经理在决定项目分工时用 `attendees` 点名项目组（`office.project.min_members`～`max_members`，默认 2～4），只点需要的人数；规则同开会（剔除名单外 / 看不了图 / 重复的，不够时按规则补齐，员工不够两位改单人办）。
- 卡片：按项目组阵容预估（`estimate_project`：项目组桌子的流水线、每份成果审查人数、覆盖参数，与实际执行一致），超过 `task_caps_usd.project`（$0.80）时弹「要不要开工」：开工 / 改单人办 / 停止。
- 项目组桌子：第一张桌子只做分诊（`handle`、`check` 跳过），完成后编排引擎另开第二张桌子：只有项目组成员上桌（代号重新分配），统筹是同一位主办经理，状态直接为已确认；不算「升级」。流水线 `office.project.pipeline`：拆分 → 自荐 → 分配 → 完成子任务 → 交叉审查 → 修改 → 逐条验收 → 合并 → 复核经理验收。和协同模式相比：不做分工讨论；交叉审查每份成果只找 `reviews_per_item`（1）位（只审关键）；合并用 `office.project.step_params` 覆盖的中等思考强度（同一步骤所有人相同）。
- 复核经理验收（`office_review`，`office_review/v1`）：主办经理以外、当前能用的另一位经理（`office_role: manager`，多位时按 seed 随机），调用记录的角色为 `reviewer`（工资单单独一行）。退回时主办经理按意见改一次（`office_revise/v1`），改后的版本即交付；没有第二位经理时跳过并注明（规则 4：经理亲自干的活由另一位经理复核）。
- 显示：网页第一张桌子「决定项目分工，项目组：……」，第二张桌子标「项目组」，复核记录与「交付 · 主办经理按验收意见修改后的版本」；右侧流程面板写明「经理」「另一位经理」；命令行「—— 项目组 ——」【复核经理验收】。

## 14. O5 已实现的内容（绩效，2026-10-22）

- 统计（`core/office/performance.py`，只从已有记录推算，不另存数据）：
  - 单人办：被派到的员工记一件；经理过目了算「验收过」，退回修改算「被退回」。
  - 开会：每位发言的员工记一件（开会不验收）。
  - 项目分工：项目组成员负责的每个子任务记一件；主办经理逐条验收过的算「验收过」，没通过的算「被退回」。
  - 每类活：件数、验收通过率、被退回次数、平均工资（该员工在这张桌子上全部调用的花费）、平均用时（调用耗时合计）。
  - 匿名未揭晓的会话不计入（不暴露身份）；只看最近 500 场办公室会话。
- 派活参考（`office.performance`：`enabled`、`min_jobs` = 3）：
  - 分诊时员工名单每行附「绩效：单人办 5 件，通过率 80%」（某类活办过 `min_jobs` 件以上才写），`office_intake/v4` 让经理在擅长和工资差不多时优先通过率高的，没有记录的照常派。
  - 规则派活（经理的分诊不能用、改派、补齐参会人 / 项目组时）只在**工资相同**的员工里优先通过率高的，不会因为绩效派给更贵的员工；没有足够记录时照旧随机。
  - 同一题所有经理看到的名单相同；绩效只看模型 id 的历史记录，不看厂商或模型名（规则 9 的「把厂商和 id 换名后结果一致」照样成立）。
- 清零：网页「员工」页绩效表的「清零」按钮（两步确认：第一次点后 5 秒内再点一次）、`roundtable performance --reset`、`POST /api/office/performance/reset`。清零只记下时刻（迁移 14 `app_settings`），之后只统计这以后创建的会话，不删除任何会话或调用记录。
- 查看：网页「员工」页名册下方的「绩效」表；`roundtable performance`；`GET /api/office` 的每位员工带 `performance`（按类型与合计）。
